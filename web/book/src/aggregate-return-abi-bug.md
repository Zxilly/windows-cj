# Bug report: aggregate-by-value COM return is miscompiled (sret / RAX mismatch)

**Status:** open — worked around in user code; root fix requires a bindgen change + regen.
**Discovered:** 2026-06-04, while porting `windows_canvas` (the failing test was `loadAndDrawBitmap`).
**Severity:** high — silently returns garbage; a naive workaround corrupts the COM object and hangs.

## Summary

When a COM interface method returns a small aggregate (struct) **by value**, the
generated binding is miscompiled on x64. The size/point/etc. comes back as
garbage. Concretely this hits every Direct2D / Direct3D / DXGI getter that
returns a structure by value, e.g.:

| Method | Returns | Size |
|---|---|---|
| `ID2D1Bitmap::GetSize` | `D2D_SIZE_F` (`{f32 width; f32 height;}`) | 8 bytes |
| `ID2D1Bitmap::GetPixelSize` | `D2D_SIZE_U` (`{u32 width; u32 height;}`) | 8 bytes |
| `ID2D1RenderTarget::GetSize` | `D2D_SIZE_F` | 8 bytes |
| `ID2D1RenderTarget::GetPixelSize` | `D2D_SIZE_U` | 8 bytes |
| `ID2D1Bitmap::GetDpi` (etc.) | `D2D_SIZE_F` / scalars | — |

The generated vtbl field for such a method looks like:

```cangjie
public var GetSize: CFunc<(CPointer<Unit>) -> Windows_..._D2D_SIZE_F> = ...
```

i.e. a value-returning `CFunc<(this) -> Aggregate>`.

## Environment

- Cangjie `cjc-version = 1.1.0`, x86_64-w64-mingw32, Windows 11 x64.
- Bindings generated by `windows_bindgen`.

## Symptom

`Bitmap.width()` / `height()` (which called `ID2D1Bitmap::GetSize`) returned
values near zero / nonsensical, failing `assert(bitmap.width() > 0)` for a
known-good 2×2 image whose true size is `(2.0, 2.0)`.

## Root cause

On the Windows x64 ABI, a C++ member function (and therefore a COM vtbl method)
that returns an aggregate which the compiler chooses to return via memory uses
the **hidden-return-pointer (sret)** convention:

- `RCX` = pointer to the caller-allocated return buffer
- `RDX` = `this`
- (further explicit args shift into `R8`, `R9`, stack)
- on return, `RAX` = the return-buffer pointer.

MSVC compiles `D2D1_SIZE_F GetSize()` this way.

The generated `CFunc<(this) -> D2D_SIZE_F>` is compiled by Cangjie with an
**inconsistent** convention:

- it **does** allocate and pass an sret buffer (so the call itself does not
  corrupt anything and does not crash), **but**
- it then **reads the return value out of `RAX`** as if the 8-byte aggregate
  were returned in a register.

Because the callee left the *buffer pointer* in `RAX` (sret convention), the
struct fields come back as the low/high 32 bits of that pointer.

### Diagnostic evidence

Reading `GetSize`'s "result" and re-joining the two `f32` fields into 64 bits
yielded `0x0000020B_94800000` and `0x0000022B_96670FF0` across runs — i.e. a
plausible user-mode heap address (~2 TB range), not `{2.0, 2.0}` (`0x40000000,
0x40000000`). That is the sret return buffer pointer, confirming the diagnosis.

## Failed workarounds (do not repeat)

1. **Read `RAX` as the value** — call the slot as `CFunc<(this) -> UInt64>` and
   split into two `f32`. This omits the sret buffer, so `this` lands in `RCX`
   (the sret slot); the callee writes the size **over the COM object's vtbl
   pointer**, corrupting it. Subsequent use of the object hangs.
2. **Manual sret** — call the slot as `CFunc<(retbuf, this) -> retbuf>` passing a
   freshly allocated buffer (tried both an `inout` `D2D_SIZE_F` and an
   `Array<Float32>` buffer, both argument orders). This **also** hung/corrupted
   in practice; Cangjie's hand-rolled multi-argument `CFunc` call for this shape
   did not behave as the sret ABI requires.

The takeaway: from user code you cannot reliably drive an sret-returning COM
method through a hand-built `CFunc`. The miscompilation is in how the *generated*
value-returning `CFunc` is lowered.

## Current workaround (in this repo)

Avoid the value-returning aggregate getter entirely; obtain the same information
through an **out-parameter** method, whose ABI (`HRESULT M(.., T* out)`) has no
sret ambiguity and is lowered correctly.

- `windows_canvas/src/bitmap.cj` reads the bitmap size via
  `IWICBitmapSource::GetSize(UINT* w, UINT* h)` at load time and caches it.
  At the default 96 DPI the WIC pixel size equals the DIP size that
  `ID2D1Bitmap::GetSize` would report, so this is behaviourally equivalent.
- `samples/windows/direct2d` computes the render-target size from the window
  client rect + DPI (`GetClientRect` is an out-param call) instead of
  `ID2D1RenderTarget::GetSize`.

Each such site is commented with a back-reference to this document.

## Expected correct implementation (the root fix)

The fix belongs in `windows_bindgen`, after which the affected packages are
**regenerated** and the workarounds can be deleted:

For any COM method whose return type is an aggregate returned by value, emit the
vtbl field and the wrapper in **explicit out-parameter (sret) form** rather than
as a value return. That is, instead of

```cangjie
public var GetSize: CFunc<(CPointer<Unit>) -> D2D_SIZE_F>
```

generate

```cangjie
// sret made explicit: (this, out: *Aggregate) -> *Aggregate
public var GetSize: CFunc<(CPointer<Unit>, CPointer<D2D_SIZE_F>) -> CPointer<D2D_SIZE_F>>
```

and have the projected accessor allocate the buffer, pass `(this, &buf)` — note
this matches the actual ABI register assignment (`RCX = retbuf`, `RDX = this`)
only if Cangjie lowers the first `CFunc` argument to `RCX`; the generator must
emit whichever argument order Cangjie's `CFunc` lowering maps to `RCX, RDX` — and
read the result from the buffer.

The cleaner alternative is a **compiler fix**: make a value-returning `CFunc`
whose return type is an aggregate that the platform ABI returns via memory read
the result from the sret buffer it already allocates, instead of from `RAX`.
That would make the existing generated signatures correct with no bindgen change.

Either way the regenerated bindings would let `vtbl.GetSize(this)` Just Work, and
the WIC / client-rect workarounds in this repo should be removed.

## Affected, audited

- `windows_canvas` — fixed via WIC out-param (above).
- `samples/windows/direct2d` — fixed via client-rect + DPI (above). Previously
  the garbage value was masked by a saturating `f32 -> u32` cast + a
  `max(200.0)` floor, which is why the clock still rendered.
- Any other sample that calls a by-value aggregate getter (`GetSize` /
  `GetPixelSize` / `GetDpi` returning a struct) is suspect and should be audited
  when touched.
